# Final Project: BaanDee Data Product Prototype

## ภาพรวมโครงงาน

ให้นักศึกษาทำงานเป็นทีม ทีมละ **3–4 คน** ภายในระยะเวลา **3 สัปดาห์** เพื่อออกแบบและพัฒนาต้นแบบ Data/AI Product สำหรับบริษัทสมมติ **BaanDee Living**

แต่ละทีมต้องเลือกปัญหาธุรกิจที่แตกต่างจากตัวอย่าง **Delayed Order Support Copilot** และสร้างระบบต้นแบบที่แสดงให้เห็นว่า ทีมสามารถเปลี่ยนข้อมูลที่ไม่สมบูรณ์ให้เป็นหลักฐานที่น่าเชื่อถือสำหรับการตัดสินใจหรือการให้บริการ หรือวิเคราะห์ ได้อย่างไร

โครงงานควรมีขอบเขตเล็กพอที่จะทำงานได้จริงภายใน 3 สัปดาห์ แต่ต้องแสดงกระบวนการครบตั้งแต่ปัญหาของผู้ใช้ ข้อมูล การทำความสะอาดข้อมูล การเชื่อมระบบ ไปจนถึงหน้าจอที่ใช้งานได้และการทดสอบพฤติกรรมสำคัญ

## โจทย์

สมมติว่าทีมของคุณเป็นทีมพัฒนาผลิตภัณฑ์ข้อมูลของ BaanDee Living ให้เลือกปัญหาหนึ่งที่พนักงาน ลูกค้า หรือผู้บริหาร ประสบอยู่ แล้วสร้างต้นแบบที่ช่วยแก้ปัญหานั้นด้วยข้อมูล 

ตัวอย่างหัวข้อที่สามารถเลือกได้ ได้แก่ (แต่ไม่จำกัด) 

- ระบบช่วยตรวจสอบสินค้าที่มีความเสี่ยงขาดสต็อก
- ระบบช่วยคัดกรองคำร้องขอคืนสินค้า
- ระบบช่วยจัดลำดับความสำคัญของงานคลังสินค้า
- ระบบสรุปและจัดหมวดหมู่ข้อร้องเรียนของลูกค้า
- ระบบช่วยตรวจสอบความพร้อมของสินค้าแต่ละสาขา
- ระบบช่วยเจ้าหน้าที่ค้นหาข้อมูลสินค้าและนโยบายที่เกี่ยวข้อง

ทีมสามารถเสนอหัวข้ออื่นในบริบท BaanDee Living ได้ แต่ **ห้ามทำ Delayed Order Support Copilot ซ้ำ**

## ผู้ใช้และคุณค่าที่ต้องอธิบาย

ทีมต้องระบุให้ชัดเจนว่า

1. ผู้ใช้หลักคือใคร
2. ผู้ใช้กำลังพยายามทำงานอะไร
3. ปัญหาในกระบวนการปัจจุบันคืออะไร
4. ต้นแบบจะช่วยให้กระบวนการดีขึ้นอย่างไร
5. ผลลัพธ์ใดเป็นเพียงสมมติฐานที่ยังต้องทดลองกับผู้ใช้จริง

## ข้อกำหนดขั้นต่ำของโครงงาน

### 1. ข้อมูล

โครงงานต้องนำข้อมูลมาเชื่อมกันอย่างน้อย **2 แหล่ง** โดยประกอบด้วย

1. ข้อมูลจากชุด BaanDee ที่อาจารย์จัดให้ อย่างน้อย 1 แหล่ง
2. ข้อมูลแหล่งใหม่ที่ทีมจัดหา ออกแบบ หรือสร้างเพิ่ม อย่างน้อย 1 แหล่ง เช่น CSV, JSON, ตารางฐานข้อมูล ข้อมูลจาก API หรือข้อมูลสังเคราะห์

การเพิ่มเพียงแถวใหม่ลงในไฟล์เดิมยังไม่นับเป็นแหล่งข้อมูลใหม่ ทีมต้องมี dataset, table, file, API หรือระบบต้นทางอีกหนึ่งแหล่งที่มีบทบาทต่างจากข้อมูลเดิม และต้องนำข้อมูลทั้งสองแหล่งมาใช้ร่วมกันในกระบวนการของระบบ

ทีมสามารถใช้ข้อมูลจากชุด BaanDee ที่ได้รับ เพิ่มแถวข้อมูล สร้างตารางใหม่ หรือสร้างข้อมูลสังเคราะห์เพิ่มเติมให้เหมาะกับโจทย์ของตนได้ โดยต้องอธิบายให้ชัดเจนว่าข้อมูลส่วนใดเป็นข้อมูลต้นฉบับ ข้อมูลส่วนใดสร้างเพิ่ม ใช้วิธีสร้างอย่างไร และตั้งสมมติฐานอะไรไว้ ห้ามแก้ทับข้อมูลต้นฉบับโดยไม่เก็บสำเนาเดิม

ทีมต้องแสดงให้เห็นอย่างน้อยว่า

- มี key หรือกฎที่ใช้เชื่อมข้อมูลระหว่างตาราง
- พบปัญหาคุณภาพข้อมูลที่แตกต่างกันอย่างน้อย 3 ปัญหา โดยทีมเป็นผู้เลือกเอง ปัญหาอาจเกิดในข้อมูลดิบ ระหว่างการเชื่อมข้อมูล หลังการแปลงข้อมูล หรือระหว่างการใช้งานระบบก็ได้ โจทย์ไม่ได้กำหนดว่าต้องเป็นปัญหาประเภทใดหรือเกิดในขั้นตอนไหน
- แสดงหลักฐานของแต่ละปัญหา วิธีตรวจพบ วิธีจัดการ และผลก่อน–หลังการจัดการ
- เก็บข้อมูลดิบไว้และสร้างข้อมูลที่ทำความสะอาดแล้วแยกต่างหาก
- บันทึกกฎหรือเหตุผลของการแก้ไขข้อมูล
- ไม่เดาหรือแก้ไขข้อมูลที่กำกวมโดยไม่มีหลักฐาน
- แยกรายการที่ตรวจสอบไม่ได้ไว้สำหรับการทบทวนของมนุษย์

ข้อมูลทั้งหมดต้องเป็นข้อมูลสังเคราะห์ ข้อมูลสาธารณะ หรือข้อมูลที่ทีมมีสิทธิใช้งาน ห้ามนำข้อมูลส่วนบุคคลจริงหรือข้อมูลลับขององค์กรมาใช้

### 2. API หรือขอบเขตระหว่างระบบ

โครงงานต้องมีขอบเขตระหว่างระบบอย่างน้อย 1 จุด เช่น REST API, webhook, database connector หรือ integration node ของเครื่องมืออย่าง n8n โดยทีมต้องอธิบายได้ว่าข้อมูลข้ามจากระบบหนึ่งไปยังอีกระบบหนึ่งอย่างไร

ระบบต้องแสดงการจัดการอย่างน้อย 3 สถานการณ์ (optional)

- ได้รับข้อมูลสำเร็จ
- ไม่พบข้อมูล
- บริการไม่พร้อมใช้งานหรือเชื่อมต่อไม่ได้

ทีมต้องสามารถชี้ให้เห็นได้ว่า code, node หรือ configuration ส่วนใดส่ง request รับข้อมูล ตรวจสอบผล และทำให้ผลลัพธ์ของระบบเปลี่ยนไปอย่างไร

### 3. ต้นแบบที่ใช้งานได้

ทีมสามารถเลือกเครื่องมือได้อย่างอิสระ เช่น Python, pandas, FastAPI, Gradio, Streamlit, JavaScript, n8n, Node-RED, Apps Script, Power Automate หรือเครื่องมืออื่นที่เหมาะกับโจทย์

การใช้ low-code หรือ no-code ไม่มีผลเสียต่อคะแนน และการเขียนโค้ดจำนวนมากไม่ได้ทำให้ได้คะแนนเพิ่มโดยอัตโนมัติ การประเมินจะพิจารณาจากคุณภาพของปัญหา ข้อมูล กระบวนการทำงาน ความน่าเชื่อถือของผลลัพธ์ และความสามารถของทีมในการอธิบายสิ่งที่สร้างขึ้น

ต้นแบบต้อง

- มีหน้าจอที่ผู้ใช้สามารถป้อนหรือเลือกกรณีศึกษาได้
- แสดงข้อมูลหรือหลักฐานที่ใช้ในการตัดสินใจ
- แสดงแหล่งที่มาและเวลาของข้อมูลเมื่อเรื่องความสดใหม่มีผลต่อคำตอบ
- แยกข้อเท็จจริงที่ยืนยันแล้วออกจากข้อมูลที่ยังไม่แน่นอน
- มีอย่างน้อย 1 กรณีทำงานสำเร็จและ 1 กรณีที่ระบบต้องหยุด ขอข้อมูลเพิ่ม หรือส่งต่อให้มนุษย์
- ผู้ใช้ต้องสามารถสร้างข้อมูลใหม่ บันทึกข้อมูล และแก้ไขข้อมูลที่มีอยู่ผ่านหน้าจอหรือ workflow ของระบบได้จริง
- ข้อมูลที่บันทึกต้องคงอยู่หลังจบคำสั่งนั้น และสามารถเรียกกลับมาแสดงเพื่อยืนยันการบันทึกและการแก้ไขได้ เช่น บันทึกใน CSV, JSON, database, Google Sheet หรือ data store ที่เหมาะสม
- หากมีการลบข้อมูล ควรใช้ soft delete หรือมีกลไกป้องกันการลบโดยไม่ตั้งใจ (optional)

ระบบต้องดำเนินการกับข้อมูลสังเคราะห์หรือข้อมูลของโครงงานเท่านั้น ไม่เชื่อมต่อเพื่อแก้ไขระบบงานจริงของมหาวิทยาลัยหรือองค์กรโดยไม่ได้รับอนุญาต ไม่บังคับใช้ GCP หรือ cloud hosting ทีมสามารถทำระบบแบบ local, self-hosted หรือ cloud-based ได้ แต่ต้องสามารถสาธิตได้จริง ควบคุมสิทธิ์การเข้าถึง และไม่เปิดเผย credential หรือข้อมูลที่ไม่ควรเผยแพร่

### 4. การใช้ AI

การใช้ Generative AI/ Agentic AI ในตัวผลิตภัณฑ์เป็น **ทางเลือก ไม่ใช่ข้อบังคับ** หากใช้ AI ทีมต้อง

- อธิบายว่า AI เพิ่มคุณค่าอะไรที่กฎปกติทำไม่ได้หรือทำได้ไม่ดี
- ส่งเฉพาะข้อมูลที่จำเป็นและตรวจสอบแล้วให้โมเดล
- ระบุข้อห้าม เช่น ห้ามสร้างวันที่ สถานะ ราคา หรือการดำเนินการที่ไม่มีหลักฐาน
- มี fallback หรือ fixture เพื่อให้สาธิตได้เมื่อ API ของโมเดลไม่พร้อม
- ตรวจสอบผลลัพธ์ก่อนแสดงต่อผู้ใช้
- ไม่บันทึก API key ลงใน GitHub

หากไม่ใช้ AI ทีมต้องอธิบายว่าทำไมกฎ การค้นหา หรือวิธีวิเคราะห์แบบปกติจึงเหมาะสมกับปัญหามากกว่า

### 5. การทดสอบ

โครงงานต้องมี test cases ที่ทำซ้ำได้อย่างน้อย **5 กรณี** จะใช้ pytest, validation script, workflow สำหรับทดสอบใน n8n, assertion node หรือวิธีอื่นที่เหมาะกับเครื่องมือก็ได้ แต่ทุกกรณีต้องระบุ input, expected result, actual result และ pass/fail อย่างชัดเจน

ส่ง URL ของ repository ที่อาจารย์สามารถเข้าถึงได้ ภายใน repository ต้องมีอย่างน้อย

```
README.md

notebooks/ หรือ scripts สำหรับแสดงกระบวนการข้อมูล

tests/ หรือ test workflow พร้อมผลที่ตรวจสอบได้

```

หากใช้ n8n ต้อง export workflow เป็นไฟล์ JSON และนำขึ้น repository โดยลบ credential, token, URL ส่วนตัว และข้อมูลลับออกก่อน หากใช้ Python ให้มี `requirements.txt` หรือไฟล์ dependency ที่เทียบเท่า หากใช้เครื่องมืออื่น ให้แนบไฟล์ export และขั้นตอนนำเข้าหรือติดตั้งที่เพียงพอให้ผู้อื่นสร้างระบบซ้ำได้

README ต้องอธิบาย

- ปัญหา ผู้ใช้ และคุณค่าที่คาดหวัง
- แผนภาพข้อมูลหรือความสัมพันธ์ระหว่างแหล่งข้อมูล
- architecture เหตุผลในการเลือกเครื่องมือ และหน้าที่ของแต่ละส่วน
- วิธีติดตั้งและเริ่มระบบทีละขั้น
- กรณีสาธิตหลักและผลลัพธ์ที่คาดหวัง
- ข้อจำกัดและสิ่งที่ยังไม่ควรนำไปใช้จริง
- บทบาทของสมาชิกแต่ละคน

ไฟล์ `AI_USE.md` ต้องระบุว่าใช้ AI ช่วยงานส่วนใด ใช้เครื่องมือใด ทีมตรวจสอบผลอย่างไร และส่วนใดที่สมาชิกเป็นผู้ตัดสินใจเอง หากไม่ได้ใช้ AI ให้ระบุว่าไม่ได้ใช้

ก่อนส่งให้สร้าง Git tag หรือ GitHub release ชื่อ `v1.0-final` และตรวจสอบว่า repository ไม่มี API key, `.env`, virtual environment, log หรือข้อมูลส่วนบุคคลจริง

ไม่ต้องส่งรายงานแยกต่างหาก เนื้อหาที่จำเป็นทั้งหมดต้องอยู่ใน repository

### 2. Demonstration

แต่ละทีมมีเวลา

- **8 นาที** สำหรับการสาธิต (ระบบอะไร มีดาต้าอะไรเพิ่มขึ้นมาจากโจทย์ที่ให้ และทำงานอย่างไร) 
- **4 นาที** สำหรับคำถามและคำตอบ

ลำดับการสาธิตที่แนะนำ

1. ปัญหาและผู้ใช้ ประมาณ 1 นาที
2. แหล่งข้อมูล ปัญหาคุณภาพข้อมูล และการแก้ไข ประมาณ 2 นาที
3. สาธิตระบบตั้งแต่ input การสร้างและบันทึกข้อมูล การเรียกกลับมาแก้ไข จนถึง output ประมาณ 3 นาที
4. แสดง failure case และ test ที่เกี่ยวข้อง ประมาณ 1 นาที
5. สรุปข้อจำกัด ความเสี่ยง และคุณค่าที่คาดหวัง ประมาณ 1 นาที

สมาชิกทุกคนต้องมีส่วนร่วมและสามารถอธิบายส่วนที่ตนรับผิดชอบได้ อาจารย์สามารถถามสมาชิกคนใดก็ได้เกี่ยวกับข้อมูล โค้ด กฎธุรกิจ หรือข้อจำกัดของระบบ

## การทำงานเป็นทีมและความซื่อสัตย์ทางวิชาการ

- ใช้ commit history, issues หรือ project board เพื่อแสดงการแบ่งงานและความคืบหน้า
- สมาชิกทุกคนต้องตรวจสอบงานของทีมและสามารถอธิบายข้อมูล โค้ด workflow หรือ configuration ที่เกี่ยวข้องได้
